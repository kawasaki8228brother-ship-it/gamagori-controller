COMMON DELIVERY AND OUTPUT CONTRACT
- Each raw candidate is ASCII, one physical line, with no terminal LF. Use the
  exact bytes from the immutable evidence commit, never reconstruct from Markdown.
- One `python -B -c` invocation is enclosed by `{ ...; }`. Every non-empty proper
  tail prefix lacks the final shell-group terminator; quoted-paste truncation also
  leaves incomplete syntax. A complete end token, decoded-payload byte count and
  SHA-256 are checked before the diagnostic body executes.
- Errors print only fixed reason codes or exception type names. No environment
  values, proxy URLs, response bodies, process arguments or per-race payloads print.
- All five candidates emit the A1-A3 v002 frame, in compact ASCII JSON lines:
  BEGIN CERTIFI_AUDIT_V002 LF
  BODY (one JSON object and LF per logical line)
  END CERTIFI_AUDIT_V002 lines=N bytes=M sha256=H LF
  N/M/H cover only exact BODY bytes including each LF, excluding BEGIN/END.
  Short summaries target about one or two phone screens; screen wrapping varies.
  Hash validation detects OCR/copy damage, not authenticity or execution approval.
  Missing END, invalid counts/hash, smart quotes, extra spaces or CRLF are STOP.
  Offline verifier: tests/verify-output.py. Examples are DUMMY data, not observations.
- Python-level audit hooks restrict file mutations, .env reads, SQLite connection
  URIs and network/subprocess use. These are not an adversarial native-code sandbox.
  SQLite native I/O is separately bounded by ro source access, exact destination,
  platform/version checks, inode checks and a Linux inotify directory watch.
  Normal interpreter site startup precedes -c; unverified startup hooks and live
  Python/virtual-environment identity remain execution prerequisites, not a PASS.

IPHONE INCOMPLETE-PASTE ABORT
If `>` or another continuation prompt appears, do NOT append a quote/brace, paste
another command, or repeatedly press Enter. Close the Render Shell screen/session.
Do not repaste until a new Shell has no pending input and the exact reviewed file
and individual execution GO are confirmed. Closing the Shell is not suspending or
restarting the service. If G3 has already started, a closed connection does NOT
prove it completed or left no partial file: treat it as STOP/UNKNOWN and do not
retry over an existing filename. Codex performs none of these Shell actions now.

G3 - B5 CONSISTENT SQLITE BACKUP (WRITE OPERATION; NOT RUN ON RENDER)
HQ13 boundary adopted: source DB opens mode=ro; necessary SQLite read-lock/read-mark
updates to EXISTING SHM are permitted. Source DB/WAL data writes, manual SHM writes,
forced checkpoints, journal_mode assignments and VACUUM are forbidden. Never claim
"zero writes to existing files". Live application writers may continue normally;
their changes are distinct from this backup reader's allowed lock bookkeeping.

Candidate sequence:
1. Fix destination to /var/data/gamagori_shadow.pre-certifi-97640c8c.YYYYMMDD.sqlite3,
   using the deployment day's JST date. If that filename or its -journal/-wal/-shm
   helper exists (including a symlink), STOP before opening SQLite. No overwrite.
   No fallback filename, deletion, rename or automatic retry is authorized.
2. Require Linux and the tested SQLite 3.50.4. Other versions/platforms require
   separate verification and a new reviewed candidate. Verify root/source regular
   files, source SQLite header and existing WAL/SHM. Read only the small header to
   identify mode; do not copy source file bytes. Observe DB/WAL sizes and disk free.
   Required free bytes = 2*(DB size + WAL size) + 64 MiB. Insufficient space STOP.
3. Start a non-persistent inotify directory watch. Lost/overflowed watches, root
   movement, unexpected filenames/events or unverified native behavior STOP.
4. Open SOURCE by SQLite URI mode=ro, query_only=ON, temp_store=MEMORY. Begin a short
   read transaction, run source integrity_check (must be the single result 'ok'),
   and read the three application-table counts. No source journal setting changes.
5. Exclusively reserve ONE new destination with O_CREAT|O_EXCL|O_NOFOLLOW, mode 0600.
   Open only that existing reserved inode with mode=rw. Use temp_store=MEMORY and
   synchronous=FULL on the new copy connection. Do not assign journal_mode anywhere.
6. Use SOURCE.backup(DESTINATION), 64 pages per step. The same source read snapshot
   is retained through integrity, counts and backup. The progress callback checks
   a 15-second cooperative deadline and at least 16 MiB remaining free space.
7. Run COPY integrity_check and compare all three table counts to the source snapshot.
   Close the copy normally, release the source read transaction, fsync the new file
   and its directory. No manual checkpoint is requested. Normal SQLite copy closure
   may consolidate its own WAL and remove its own temporary helper files.
8. Check source/destination inode identities and final directory scope. Only the
   new completed backup may remain; copy helper residue is STOP. Compute backup size
   and SHA-256 from the reserved descriptor after close/fsync. Reject size/mtime
   changes during hashing, deadline expiry, unexpected transient events or new files.

The SQLite 3.50.4 Linux fixture observation found these COPY helpers generated and
removed normally: BACKUP-journal, BACKUP-wal, BACKUP-shm. They are not extra completed
backup products. inotify allows only the exact new backup and those three suffixes;
unknown helpers, even if subsequently deleted, STOP. Source WAL/SHM must pre-exist.
Source data changes are blocked by mode=ro/query_only. Source DB/WAL modification
events caused by the independently running worker are not mistaken for writes by
this reader. Their attribution cannot be proved from a directory event alone.
Controlled no-writer tests therefore check source DB/WAL fingerprints separately;
the concurrent-writer test explicitly attributes writes to its fixture writer.
The ordinary SHM read-mark change is recorded separately in the native-I/O log.

Failure: keep any new/partial/unverified file, report STOP with stage and type/code,
close owned handles, and do not delete/repair/checkpoint it. A retained file is not
a valid backup merely because it has a SQLite header. Existing filename blocks a
retry. Recovery or an alternative reviewed filename needs a separate HQ decision.
The deadline is cooperative SQLite/progress/hash monitoring, not a guarantee against
an indefinitely stalled kernel I/O. Loss of END or uncertain completion is STOP.
No full copy of the live .db, wal or shm is made with cp/shutil/read-write loops.
Source header reads and copy-only checksum reads are not the backup mechanism.
No backup file is uploaded by these candidates. Mode 0600 and a private retention
plan are prerequisites because the real backup can contain confidential state.

ISOLATION TRUST AND LIMITATIONS
Tests use only disposable local SQLite fixtures and loopback TLS servers, with
explicit test CA/trust_env overrides confined to those fixture clients. Those are
not external HQ12 results. HTTPX MockTransport is used only to inject DNS/timeout/
proxy/403/redirect failures. The app's production behavior is not simulated as fact.
Claude independent audit, actual Render filesystem/VFS/startup/runtime conditions,
and all production execution approvals remain pending. No unknown behavior is
worked around by changing versions, journal modes, source settings or app state.
